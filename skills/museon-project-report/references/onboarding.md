# First-run onboarding

Complete these stages in order. Reuse authorization and choices already established in the user's session; do not ask again for known answers.

1. **Check installation.** Locate `museoncli`, run `museoncli version`, and inspect `museoncli schema`. If absent, explain the prerequisite and guide the user to the official Museon-AI/museon-cli release installation. The verified release is `https://github.com/Museon-AI/museon-cli/releases/tag/v0.6.0`; inspect its current instructions before recommending an installation command. Do not silently install Python/uv or change an existing CLI. Check `lark-cli` when Feishu is selected, using its own installed help and official installation guidance.
2. **Login and authorization.** Inspect CLI auth help and use the CLI-provided interactive login flow. Let the user complete authorization; never request a pasted password or token. Verify the selected Museon workspace and Feishu sending identity. For Feishu use `lark-cli auth status --json --verify`; user and bot visibility differ. If setup/auth guidance is available in the host's `museon-cli` and `lark-shared` skills, read the applicable instructions. Otherwise inspect installed help; do not guess auth commands. Login success alone does not prove access to a project or recipient.
3. **Project selection.** Discover accessible workspaces through the installed CLI schema/help, then paginate `campaign-monitor +list` within each selected workspace. Read its schema first. Present actual project names and workspace context, let the user select multiple projects, and save canonical IDs and a timezone for each. Preserve mappings across later runs. A user may select warmup-only or promotion-only projects; both report sections still exist. Collector lists workspace videos and filters campaign IDs locally because the 0.6.0 video-list filter does not accept campaign_id.
4. **Timing.** Offer daily fixed local times, interval summaries, and actual-publication-relative checkpoints. Default proposal: 30/120/360 minutes, polling every 5 minutes; daily summary is optional. These are proposals until selected. Explain up to one poll interval of timing delay, platform sync lag, and host availability. Confirm catch-up behavior after downtime (default proposal: coalesce due triggers from the last 180 minutes; older missed triggers are not backfilled). Multiple triggers within one project poll become one card. Set history_days long enough to include all monitored publishing schedules and expected manual publication delays. Expand history if older schedules remain monitored.
5. **Channel and test.** Select self or a specific group, with explicit sender identity and verified recipient. Resolve IDs via the same Feishu application; never reuse IDs across applications. Check the bot is available in the target group or direct chat. Show the complete configuration and generate a real-data V5 preview. If the user has authorized sending the test, send once through Feishu CLI and read back. The test trigger is explicit and does not enable recurring execution.
6. **Activate.** After the user accepts the test and schedule, set enabled=true and create/update the supported host scheduler. In Codex use the automation tool, following its schema; default to the current thread heartbeat. Discover existing matching automations before creating one. If that tool is unavailable, describe the scheduler dependency and stop short of claiming activation. Do not implement hidden cron/launchd fallbacks. On first activation, agree whether catch-up triggers should send immediately or be baseline-marked as skipped; never silently send a backlog.
7. **Adjust.** Support changing projects, checkpoint offsets, daily times, intervals, channel, timezone, history window, and display fields; pause/resume without re-onboarding. Update the existing automation. Resolve any uncertain pending delivery before changing its destination; completed delivery keys include destination so channel changes are explicit. Test changed delivery settings once when authorized.

The installation ZIP contains no credentials, project IDs, recipient IDs, delivery state or private post samples. A test card sent during this conversation is evidence of the layout, not proof that a newly installed user's authentication or scheduler works.
