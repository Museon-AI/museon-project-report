# First-run onboarding

Complete these stages in order. Reuse authorization and choices already established in the user's session; do not ask again for known answers.

1. **Check installation.** Locate `museoncli`, run `museoncli version`, and inspect `museoncli schema`. If absent, explain the prerequisite and guide the user to the official Museon-AI/museon-cli release installation. The verified release is `https://github.com/Museon-AI/museon-cli/releases/tag/v0.6.0`; inspect its current instructions before recommending an installation command. When the user has requested installation and setup, install missing dependencies within that scope after explaining the action. Preserve working existing tools; do not silently upgrade or downgrade them. Check `lark-cli` when Feishu is selected, using its own installed help and official installation guidance.
2. **Login and authorization.** Inspect CLI auth help and use the CLI-provided interactive login flow. Let the user complete authorization; never request a pasted password or token. Verify the selected Museon workspace and Feishu sending identity. For Feishu use `lark-cli auth status --json --verify`; user and bot visibility differ. If setup/auth guidance is available in the host's `museon-cli` and `lark-shared` skills, read the applicable instructions. Otherwise inspect installed help; do not guess auth commands. Login success alone does not prove access to a project or recipient.
3. **Project selection.** Discover accessible workspaces through the installed CLI schema/help, then paginate `campaign-monitor +list` within each selected workspace. Read its schema first. Present actual project names and workspace context, let the user select multiple projects, and save canonical IDs and a timezone for each. Preserve mappings across later runs. A user may select warmup-only or promotion-only projects; both report sections still exist. Collector lists workspace videos and filters campaign IDs locally because the 0.6.0 video-list filter does not accept campaign_id.
4. **Timing.** Offer daily fixed local times, interval summaries, and actual-publication-relative checkpoints. Default proposal: 30/120/360 minutes, polling every 5 minutes; daily summary is optional. These are proposals until selected. Explain up to one poll interval of timing delay, platform sync lag, and host availability. Confirm catch-up behavior after downtime (default proposal: coalesce due triggers from the last 180 minutes; older missed triggers are not backfilled). Multiple triggers within one project poll become one card. Set history_days long enough to include all monitored publishing schedules and expected manual publication delays. Expand history if older schedules remain monitored.
5. **Channel and test.** Select self or a specific group, with explicit sender identity and verified recipient. Resolve IDs via the same Feishu application; never reuse IDs across applications. Check the bot is available in the target group or direct chat. Show the complete configuration and generate a real-data V5 preview. If the user has authorized sending the test, send once through Feishu CLI and read back. The test trigger is explicit and does not enable recurring execution.
6. **Activate.** After the user accepts the test and schedule, set enabled=true and create/update the supported host scheduler. In Codex use the automation tool, following its schema; default to the current thread heartbeat. Discover existing matching automations before creating one. If that tool is unavailable, describe the scheduler dependency and stop short of claiming activation. Do not implement hidden cron/launchd fallbacks. On first activation, agree whether catch-up triggers should send immediately or be baseline-marked as skipped; never silently send a backlog.
7. **Adjust.** Support changing projects, checkpoint offsets, daily times, intervals, channel, timezone, history window, and display fields; pause/resume without re-onboarding. Update the existing automation. Resolve any uncertain pending delivery before changing its destination; completed delivery keys include destination so channel changes are explicit. Test changed delivery settings once when authorized.

The installation ZIP contains no credentials, project IDs, recipient IDs, delivery state or private post samples. A test card sent during this conversation is evidence of the layout, not proof that a newly installed user's authentication or scheduler works.

## Missing tools and first Feishu setup

Handle these branches as part of onboarding; sales users should not have to find separate installation instructions. Check executables and versions before acting. Reuse existing compatible installations, profiles and authorization. Read available host skills only when relevant; this package must also work without them.

- **Runtime:** Python 3.11+ is required. Use official Python/uv installation instructions for the detected OS if missing. Verify the resulting interpreter. Native Windows cannot run the delivery helper because it imports `fcntl`; offer a Linux/WSL setup and verify it there before claiming success.
- **Museon:** use the official release instructions at https://github.com/Museon-AI/museon-cli/releases/tag/v0.6.0. With uv already installed, an isolated invocation is `uvx --from https://github.com/Museon-AI/museon-cli/releases/download/v0.6.0/museoncli-0.6.0-py3-none-any.whl museoncli`. Save the full invocation as the config `cli` argv array when using this route. Inspect its auth help, complete interactive login, then prove project access with a real list request. Never substitute the unrelated staff CLI from a local monorepo.
- **Feishu CLI missing:** consult https://github.com/larksuite/cli/blob/main/README.zh.md. The official npm installer is `npx @larksuite/cli@latest install`; verify Node/npm availability first and handle the installer prompts. The package is `@larksuite/cli`, executable `lark-cli`; do not install the unrelated PyPI package with the same executable name. Verify command help after installation.
- **Feishu app missing:** inspect `lark-cli config --help` and existing configuration without exposing secrets. Reuse a suitable configured application/profile. If none exists, inspect `lark-cli config init --help`; the documented new-app flow is `lark-cli config init --new`. It waits for browser completion, so launch it with a resumable process session and show its verification link. Use a named profile when necessary to avoid overwriting another integration. In OpenClaw/Hermes environments, inspect `config bind` to reuse the existing Agent app; do not force a new app past the environment guard. If an administrator must approve app creation or permissions, provide the exact task/link and wait for that approval.
- **Feishu user authorization missing/expired:** inspect installed auth help. `lark-cli auth login --domain im --no-wait --json` starts the documented messaging login; show its verification link/QR and finish using the returned device code as directed by CLI help. Request only the domains/scopes needed for the selected workflow. Verify with `lark-cli auth status --json --verify`. Never store the temporary device code in this skill's state.
- **Bot delivery:** user login does not grant bot app permissions. Verify the selected bot/app has messaging permission and can reach the recipient; for groups, verify membership/availability. Check this using the exact identity/profile the delivery helper will inherit, including in the scheduler environment. Never silently switch identities to bypass missing access.

## Resume and completion evidence

After each completed stage, atomically write a small local `~/.config/museon-project-report/onboarding.json`: schema version, installed release, completed stages, selected non-secret profile name, config path, last blocker and next action, test receipt ID, and scheduler ID when available. Keep credentials, authorization URLs/device codes and raw command output out. Restrict local state to the current user. Configuration and delivery history remain outside the installed skill and public ZIP.

On “继续配置”, load progress and existing config, recheck live dependencies/auth/access and continue from the first unmet stage. A recorded stage is a hint, not proof that an expired login still works. Do not reset project choices, repeat a successful test send or recreate an existing automation. An interrupted send with an uncertain result must be reconciled before retrying.

Report each status accurately: installed / awaiting login or admin / configured / test verified / scheduled. Only report scheduled when the actual host scheduler returns an identifier and its schedule is read back. Include selected projects, timezone, recipient, next check time, and offline/catch-up behavior. When the host cannot support the selected cadence, offer a supported cadence and obtain the user's choice; never report a five-minute schedule that the host did not accept. Installation never implies activation.

If setup is blocked, give one plain-language explanation and the next action:

| Observed problem | Next action |
| --- | --- |
| Download unavailable | Use the user's local release ZIP; resume setup after installation. |
| CLI not found after install | Check the actual install location/PATH and restart or configure the calling environment; do not reinstall blindly. |
| User login expired | Resume the CLI browser login and verify it. |
| App permission/admin approval missing | Name the missing permission and provide the app admin link from the CLI; user re-login alone will not fix bot permissions. |
| Customer project absent | Confirm workspace/account and ask the project owner for access; do not invent an ID. |
| Group not visible or bot unavailable | Confirm the target group and arrange the selected app's access; do not send to another group. |
| Keychain/credential store unavailable in scheduled run | Recover interactively in the same runtime/profile; do not copy credentials into report config. |
| Host offline or cadence unsupported | Explain delayed checks/catch-up or choose a supported host schedule before activation. |

Updates: make a timestamped local backup of the installed skill before replacement, preserve config/progress/delivery state, record the new release, and validate before resuming. Restore the local backup if validation fails. Never upload personal backups to the public repository.

Save the selected Feishu profile as `destination.profile` in the report config (a non-empty profile name, no credentials). The delivery helper passes `--profile` explicitly on both send and readback; profile is also part of the destination deduplication key. Resolve old pending receipts before switching profiles. Existing configs without this field retain CLI default behavior; during onboarding resolve and pin the effective profile using `lark-cli whoami` and verify the same explicit profile in the scheduler environment.
